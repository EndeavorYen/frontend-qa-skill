# Critic 關卡

寫報告之前，用一個沒有參與測試的視角，逐條重新驗證 `findings.md`。測試時的 agent 容易被自己的推論帶著走：看到畫面不對，就認定是某個原因；或者只看了一半就下結論。Critic 只看證據，重新做一次，把不成立的擋在報告外面。

## 誰來當 Critic

- **子代理（建議）**：開一個新的子代理（subagent），只帶入下面「帶入什麼」列出的內容，不帶主 session 的對話紀錄。這樣它不會被測試時的推論影響
- **主 session 自查**：沒有取得同意，或執行環境沒有開子代理的工具時，主 session 照同一張檢查表自己做一次。主 session 沒辦法忘掉測試時的推論，所以自查只能做到：只照 `findings.md` 的文字步驟重做，不參考測試時的筆記；P3 改看證據。在 `report.md` 寫明是自查

### 取得同意

步驟 0 和深度一起問一次：「寫報告前要不要開一個子代理，逐條重新驗證問題？會多花一些成本，但可以減少誤報。」

- 使用者同意：用子代理
- 不同意或沒有回答：主 session 自查
- 無人值守：只有指令明確允許（例如「允許 Critic 子代理」「可以開子代理」）才用子代理，否則自查

## 帶入什麼

- `findings.md` 全文
- `shots/` 的路徑（不要把截圖讀進主 session 再轉交）
- `tool-track.md` 全文，以及 SKILL.md 的「歸因規則」：工具有哪些已知問題、測試時用了什麼替代做法（例如某個操作要改用 `eval` 才觸發得到），Critic 重做時要照用
- 目標 URL、分頁 id、測試帳號、環境、禁止動作
- SKILL.md 的「證據規則」「護欄」，以及 [severity.md](severity.md)

不要帶入：主 session 的對話紀錄、測試時的猜測、`ux-review.md`。`ux-review.md` 留到下面的「體檢複核」，那時 findings 裡哪些 F 會被刪除已經知道了。

## 怎麼驗證

| 等級 | 做法 |
|---|---|
| P0、P1 | 從乾淨狀態照重現步驟重做 2 次（和證據規則相同） |
| P2 | 照重現步驟重做 1 次；沒重現的話，再從乾淨狀態做第 2 次 |
| P3 | 看截圖和證據判斷；證據不足時才重做 |

乾淨狀態是步驟 1 的 `checkpoint.json`：`restore <t> --file .frontend-qa/<run>/checkpoint.json --format json`，再 `perceive <t>`，然後照步驟操作。`restore` 只還原這個分頁的 URL、cookie 和 storage，不還原後端資料。測試輪中途 app 自己登出時，`restore` 把 session 寫回 storage，頁面仍停在 `#/login`；先 `reload <t>` 再 `perceive <t>`，頁面才會讀到還原後的 session。

**有副作用的 finding**：重做會寫入資料、扣款、寄信或通知的（例如重複建立、重複扣款），重做前先照步驟 0 的禁止動作判斷：正式環境不重做，改看證據判斷；非正式環境要先知道怎麼回到乾淨狀態（重設資料、換一筆新資料）。只跑 `restore` 不夠，因為後端資料還在。不知道怎麼清掉後端資料的話也改看證據。改看證據的，在理由寫「未重做：有副作用」。

**重做失敗不等於不成立**：重做沒出現時，先照歸因規則判斷是不是工具的問題（換一種操作方式再試）。P0、P1 主 session 已經從乾淨狀態重現過 2 次，Critic 重做失敗、或因為有副作用而沒有重做時，都不能判 `不成立`，最多判 `待確認`，交回主 session 再驗一次。

**失敗要給下一步**：重做失敗、驅動指令報錯，或這一條沒有做完時，理由要寫明原因，並給一條可以直接複製執行的下一步指令，三選一：`CDP_PORT=<port> node skills/frontend-qa/scripts/probe.mjs <probe.json> --out <probe-result.json>`、被測目標自己的重現指令（`cd .frontend-qa/<run>/repro && BASE_URL=<網址> npx --no-install playwright test --reporter=line`，見 [repro.md](repro.md#驗證腳本)）、或剛剛失敗的那一條驅動指令原樣。`BASE_URL=<網址> npx playwright test -c <repo>/evals/repro` 只適用於 seeded-app 評測（見 `evals/repro/README.md`），不要拿去跑別的網站。

Critic 重做時遇到的工具問題，寫在判定的理由裡，主 session 收到後照歸因規則補進 `tool-track.md`。

每一條都要回答三個問題：
1. 照步驟做，看得到描述的現象嗎？
2. 現象的範圍和描述一樣嗎？例如描述說「三個匯出格式都壞了」，實際上只有一個壞，就是部分成立
3. 等級合理嗎？對照 [severity.md](severity.md)

## 結果

寫在執行目錄的 `critic-verdicts.md`：

```markdown
| F | 判定 | 理由 | 等級建議 | 主 session 處理 |
|---|---|---|---|---|
| F3 | 成立 | 照步驟重做 2 次都重現 | P1（不變） | — |
| F9 | 部分成立 | 「匯出的 CSV 少了欄位」只少了『負責人』一欄，描述中的『到期日』其實有匯出 | P2（不變） | 已改寫 |
| F14 | 不成立 | 從乾淨狀態重做 2 次都沒有出現，換成 `eval` 操作也一樣；證據：`shots/F14-half-loaded.png`（載入到一半時拍的） | — | 已刪除 |
| F2 | 待確認 | P1，重做 2 次沒出現，但工具軌記錄 `click` 這幾次回報不穩定 | — | 讀 DOM 確認重現，成立；`shots/F2-recheck.png` |
```

判定只能是 `成立`、`部分成立`、`不成立`、`待確認`。

判 `不成立`（不是問題，要從報告拿掉）時，理由必須附上證據，至少一種：`shots/` 的截圖路徑、重現腳本路徑，或 `probe-result.json` 的那一筆。沒有證據就不能判 `不成立`，改判 `待確認`。

## 主 session 收到結果之後

- `不成立`：從 `findings.md` 刪除，不要進報告。理由和證據留在 `critic-verdicts.md`，之後要查還找得到。證據不足的不能當 `不成立`
- `待確認`：主 session 從乾淨狀態再重現一次，而且至少換一種觀察方式（例如讀 DOM 狀態、等頁面穩定後再截圖），附上新的證據。重現了就是 `成立`；沒重現就照歸因規則，記到工具軌或 `unattributed.md`（這一筆要附截圖路徑、重現腳本或探測結果至少一種），不要進報告。這次重做若失敗，處理欄同時寫原因和一條可執行的下一步指令。結果寫進「主 session 處理」欄
- `部分成立`：改寫那一筆，只留成立的部分，在證據加上 Critic 的理由
- 等級建議和原本不同：照 [severity.md](severity.md) 重新判斷，決定後在那一筆註明
- 搜尋 `ux-review.md` 有沒有引用被刪掉或改寫的 F 編號。有的話，換成其他證據，或重新評那個維度的分數
- `report.md` 寫上 Critic 的方式（子代理或自查）、findings 各種判定的筆數，以及體檢判定的筆數（見下方「體檢複核」）

## 體檢複核

同一個 Critic 做（子代理或主 session 自查，取得同意的方式不變）。排在逐條驗證 findings、而且主 session 已經刪掉 `不成立`、改寫 `部分成立` 之後，這樣才知道哪些 F 編號已經被刪除。不要為了這一節另開一個看得到主 session 對話的代理。沒有 `ux-review.md` 就跳過，例如 `audit`。

不重新評整份體檢，只檢查下表的條件。不改 7 個維度和分數錨點。

### 帶入什麼

- `ux-review.md`
- `critic-verdicts.md` 裡的 findings 判定
- 量化檢查結果（`ux-review.md` 的量化檢查，或 `probe-result.json`）
- `.frontend-qa/state/design-context.md`（有的話）。只用在判斷扣分理由是不是落在別的維度，不用它重打分數
- `shots/` 的路徑（不要把截圖讀進主 session 再轉交）

不要帶入：主 session 的對話紀錄。

### 逐條檢查

每個分數都寫一列；3 分以下為必填。

| 檢查 | 不通過的條件 |
|---|---|
| 指到元素 | 評論沒有 selector、元素文字或座標 |
| 證據 | 3 分以下沒有 F 編號、截圖或量化數字；或者引用的 F 已經被判 `不成立` |
| 維度歸屬 | 扣分理由屬於別的維度（對照 [ux-review.md](ux-review.md#7-個維度) 的「要問的問題」） |
| 跨畫面一致 | 同一個共用元件的問題，在有用到它的畫面扣分不同 |
| 預設 4 分 | 給 4 分的評論沒有寫「要到 5 分需要什麼」 |
| 建議可執行 | 「最值得做的 5 項改善」中有「優化體驗」這類無法動手的寫法 |

結果寫在 `critic-verdicts.md` 的第二張表，接在 findings 那張表後面：

```markdown
| 畫面 | 維度 | 原分 | 判定 | 建議分 | 理由 |
|---|---|---|---|---|---|
| S2 | 視覺層級 | 2 | 調整 | 3 | 扣分理由是 F31 載入失敗，屬於回饋維度 |
```

判定只能是 `維持`、`調整`、`證據不足`。

對上表的對應：

- 指到元素不通過，或證據不通過：`證據不足`。建議分先寫補不到證據時要改成的分數：低於 3 的往 3 靠，高於 3 的往 3 靠，已經是 3 就寫 3
- 維度歸屬不通過：`調整`。建議分拿掉不屬於這個維度的理由後，只按這個維度的錨點重估
- 跨畫面一致不通過：`調整`。建議分改成有用到該元件的畫面裡較低的那個分數
- 預設 4 分不通過：`調整`，建議分 3
- 建議可執行不通過：加一列，畫面寫 `—`，維度寫 `最值得做的 5 項改善`，原分和建議分寫 `—`，判定 `調整`，理由指出哪一項無法動手
- 同一則評論踩到多條時，缺證據用 `證據不足`，否則用 `調整`
- 都沒踩到：`維持`，建議分等於原分

### 主 session 收到體檢判定之後

- `調整`：照建議分改 `ux-review.md` 的分數和平均，或在那則評論寫出不採用的理由
- `證據不足`：補上 F 編號、截圖或量化數字。補不到就往 3 分靠攏
- `維持`：不改分數
- `report.md` 的 Critic 統計加上體檢判定的筆數：維持 n、調整 n、證據不足 n
