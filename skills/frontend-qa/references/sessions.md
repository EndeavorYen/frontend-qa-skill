# 分 session 執行

成本大約是「輪數 × 平均對話長度」。所有測試輪都在同一個對話中跑的話，對話會一路變長，後面每一輪都要重讀前面的紀錄。分 session 執行時，每個測試輪和體檢各用一個新的子 session，只帶入那一輪需要的內容，所以每個 session 的對話都很短。

代價：
- 會開多個子代理（subagent），所以一定要先取得使用者同意
- 各輪看不到上一輪的細節，只看得到 `findings.md` 的標題清單，所以主 session 合併時要另外去除重複

## 取得同意

步驟 0 和深度一起問一次：「要不要分 session 執行？每個測試輪和體檢會各開一個子代理，依序執行，可以降低成本。」

- 使用者同意：用分 session 執行
- 使用者不同意、沒有回答，或執行環境沒有開子代理的工具：用單一 session，照原本的步驟 2、3 執行
- 無人值守：只有指令明確允許分 session（例如「允許分 session 執行」「可以開子代理」）時才用；沒寫就用單一 session

在 `report.md` 開頭記下用的是哪一種模式。

## 主 session 做什麼

主 session 負責步驟 0、1、4、5、6，以及依序派出子 session。

1. 步驟 1 完成後，覆蓋地圖、`report.md` 的估算都已經寫好
2. 依開啟的測試輪順序，一次派出一個子 session，等它結束再派下一個。**不要並行**：各輪共用同一個瀏覽器分頁和同一份 app 資料，並行會互相干擾
3. 每個子 session 結束後，讀它回報的一行摘要，並確認覆蓋地圖那一欄沒有 `☐`。還有 `☐` 的話，再派一次同一輪，只帶入還沒測的列
4. 體檢有開的話，最後派一個體檢子 session
5. 全部結束後，主 session 做步驟 4 的合併與分級

## 子 session 帶入什麼

只帶入以下內容，不要把主 session 的對話紀錄或其他輪的細節傳過去：

- 執行目錄的路徑，以及 `coverage.md` 的內容
- 步驟 0 的範圍、禁止動作、視窗尺寸、深度，以及工具軌是否開啟
- 這一輪需要的 reference：
  - 測試輪：`personas.md` 開頭的說明和這一輪的段落、`severity.md`、`report-template.md` 的 findings.md 格式；`狀態` 這一輪再加 `state-checklist.md`
  - 體檢：`ux-review.md`
  - 工具軌開啟時，每一輪都帶 `tool-track.md`
- `findings.md` 目前的標題清單（`grep '^### F' findings.md` 的結果，一行一筆），用來避免重複回報
- SKILL.md 的「歸因規則」「證據規則」「護欄」三節

## 子 session 的產出

- 新發現的問題寫進 `findings.md`，編號接在現有最大的 F 編號之後
- 把 `coverage.md` 中自己那一欄的 `☐` 改成 `✅`、`➖ <理由>` 或 `⛔ <工具軌編號>`，不要動其他欄
- 工具問題寫進 `tool-track.md`，判斷不出來的寫進 `unattributed.md`
- 體檢子 session 寫 `ux-review.md`，並更新覆蓋地圖的 `體檢` 欄
- 結束時只回報一行：`<輪名>：新增 F<a>–F<b>，☐ 剩 <n> 格`

## 合併與去重

步驟 4 由主 session 做。因為各輪只看得到標題，同一個問題可能被不同輪各記一次：

- 同一個畫面、同一個現象，就算重複，即使描述的角度不同
- 合併時保留最小的 F 編號，把其他編號寫在那一筆的備註，例如「合併 F12、F27」，並保留各輪的證據
- 體檢中引用到被合併的 F 編號，要改成保留下來的編號
