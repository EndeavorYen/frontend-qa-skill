# UI/UX 體檢

體檢回答的問題是：「這個畫面做得好不好？要怎麼改才會更好？」它和找缺陷是兩件事：
- 「按鈕圓角不一致」是一個缺陷，寫在 `findings.md`。
- 「整個表單看起來不可信」是體檢的結論，寫在 `ux-review.md`，並附上改善建議。

體檢可以引用缺陷（F 編號）當作證據，但不要把缺陷重寫一遍。

## 程度

| 程度 | 做什麼 |
|---|---|
| 輕 | 每個畫面只評「整體」一個分數，附一句理由 |
| 標準 | 每個畫面評 7 個維度，附改善建議 |
| 深 | 標準的內容，再加上「量化檢查」 |

## 7 個維度

每個維度打 1–5 分。分數的意思：

- **5**：可以直接拿來當設計範例
- **4**：只有小瑕疵，一般使用者不會注意到
- **3**：可以用，但明顯粗糙，或有地方讓人猶豫
- **2**：使用者會困惑、操作出錯，或覺得不可信
- **1**：嚴重妨礙使用

| 維度 | 要問的問題 |
|---|---|
| **視覺層級** | 主要動作是不是一眼就看得到？標題、內容、次要資訊的輕重分得清楚嗎？ |
| **一致性** | 同類元件（按鈕、卡片、表單、用詞）在這個畫面和其他畫面長得一樣、叫一樣的名字嗎？ |
| **排版節奏** | 有沒有對齊？間距有沒有規律？資訊密度合不合理？在手機上排得好嗎？ |
| **回饋** | 載入中、成功、失敗、停用，使用者都看得到嗎？操作後馬上知道發生了什麼嗎？ |
| **文案** | 標題、按鈕、錯誤訊息、提示文字清楚嗎？語氣一致嗎？用的是使用者的語言嗎？ |
| **效率** | 完成這個畫面的主要任務要幾步？有沒有多餘的步驟？預設值合理嗎？ |
| **質感** | 整體看起來專業、可信嗎？會讓人願意把資料或錢交給它嗎？ |

### 分數錨點

上面的定義太抽象時，用下面這些看得到的狀況對照。**錨點只套用在和這個維度有關的現象上**：一個維度只看屬於它的問題（見上表「要問的問題」），別的維度或別的畫面的 bug 不能拉低它。例如設定頁「儲存沒有真的存」是回饋的問題，不會讓同一頁的視覺層級或文案變低。同一個維度同時符合兩個分數的描述時，取低的那個。

| 分數 | 這個維度看得到的狀況 |
|---|---|
| 5 | 這個維度找不到可以改的地方；拿給設計師看，對方也挑不出問題 |
| 4 | 這個維度只剩要刻意找才看得到的瑕疵（例如某個間距差 4px），使用者不會因此停下來 |
| 3 | 這個維度至少有一處讓人停下來想、找、或試第二次；或者有一眼就看得出來的粗糙（對不齊、用詞不一） |
| 2 | 這個維度有會讓使用者做錯、找不到、或懷疑結果的地方，例如主要動作要找才找得到、按了不知道成功沒有、看到 `undefined` |
| 1 | 這個維度的問題讓主要任務做不完，或做完了卻是錯的結果 |

### 評論要指到元素

每條評論都要指出畫面上具體的元素：selector、元素上的文字，或座標。「整個畫面很亂」「表單不好用」這種沒有指到任何元素的評論不算，分數也不能只靠它。

### 好的評論和差的評論

下面的例子來自一個虛構的專案管理 app。差的評論不是錯，而是別人拿到後不知道哪裡有問題、要改什麼。

| 維度 | 差的評論 | 好的評論 |
|---|---|---|
| 視覺層級 3 | 「頁面重點不明顯。」 | 「專案列表頁有三顆一樣是實心藍色的按鈕：`新增專案`、`匯入`、`匯出`（右上角 x=1180–1400）。新增是主要動作，但三顆看起來一樣重，第一次來的人要讀完三個字才知道按哪個。要到 4：只留 `新增專案` 實心，另外兩個改成外框按鈕。」 |
| 一致性 2 | 「日期格式不統一。」 | 「同一個截止日在三個地方長得不一樣：列表 `.due` 是 `2026/10/06`、詳情頁 `#due` 是 `10-06`、通知中心是 `昨天`。使用者要自己換算才知道是不是同一天，跨年時 `10-06` 也分不出是哪一年。」 |
| 回饋 3 | 「回饋還不錯。」 | 「拖曳看板卡片（`.card`）到另一欄後，卡片立刻移過去，重新整理後位置仍然保留；拖到不允許的欄位時卡片會彈回原位並顯示原因。扣分是因為上傳附件（`#attach`）時沒有進度，大檔案要等十幾秒，中間會讓人猶豫要不要再按一次。要到 4：上傳時顯示進度條。」 |
| 文案 3 | 「對話框的按鈕不清楚。」 | 「離開編輯頁時的對話框問『要放棄變更嗎？』，按鈕卻是 `確定` / `取消`（`.modal-footer`）。`確定` 是確定放棄還是確定儲存，要停下來想。改成 `放棄變更` / `繼續編輯`。」 |
| 排版節奏 3 | 「看板很亂。」 | 「看板頁三欄（`.column`）的卡片間距分別是 16px、24px、12px，欄標題的基線也差了 6px，掃過去會覺得三欄不是同一個元件。卡片內的標籤（`.tag`）在標題很長時被擠到第二行，和沒換行的卡片高度不齊。」 |

規則：
- 3 分以下一定要附證據：F 編號、截圖，或量化檢查的數字。
- 不要預設給 4 分。沒有具體理由的話，分數就往 3 靠攏，並寫出「需要什麼才會到 4」。
- 評分的依據是你在測試輪中實際操作的體驗，不是看一眼截圖的印象。
- 需要看畫面時，沿用設計師輪看過的那張截圖；設計師輪沒開、或那個尺寸沒看過，才看一張。不要為了體檢重拍、重看（看圖額度見 SKILL.md「截圖規則」）。

## 量化檢查

程度為「深」時，每個畫面在桌機和手機尺寸各跑一次下面的程式碼（`eval <t> "<下列程式碼>"`），再把結果記到 `ux-review.md`：

```js
(() => {
  const visible = (e) => e.getClientRects().length > 0 && getComputedStyle(e).visibility !== 'hidden';
  const text = [...document.querySelectorAll('body *')].filter((e) => visible(e) && [...e.childNodes].some((n) => n.nodeType === 3 && n.textContent.trim()));
  const controls = [...document.querySelectorAll('a,button,input,select,textarea,[role=button],[onclick]')].filter(visible);
  const uniq = (list) => [...new Set(list)];
  const cs = (e) => getComputedStyle(e);
  return JSON.stringify({
    fontSizes: uniq(text.map((e) => cs(e).fontSize)),
    fontWeights: uniq(text.map((e) => cs(e).fontWeight)),
    textColors: uniq(text.map((e) => cs(e).color)),
    radii: uniq(controls.map((e) => cs(e).borderRadius)).filter((r) => r !== '0px'),
    smallTargets: controls.filter((e) => { const r = e.getBoundingClientRect(); return r.width < 44 || r.height < 44; }).map((e) => (e.innerText || e.getAttribute('aria-label') || e.tagName).trim().slice(0, 20)),
    horizontalOverflow: document.documentElement.scrollWidth > innerWidth,
  });
})()
```

判讀方式（超過門檻不一定就是錯，但要寫出理由）：

| 項目 | 門檻 | 對應維度 |
|---|---|---|
| 字級種類 | 超過 6 種 | 一致性、視覺層級 |
| 字重種類 | 超過 3 種 | 一致性 |
| 文字顏色 | 超過 5 種 | 一致性 |
| 圓角種類 | 超過 2 種 | 一致性 |
| 小於 44px 的點擊目標 | 手機尺寸下有任何一個 | 排版節奏、效率 |
| 橫向溢出 | `true` | 排版節奏 |

文字和背景的對比度用 `styles <t> <sel>` 讀出前景色和背景色後計算。一般文字低於 4.5:1 要記錄下來。

## ux-review.md 格式

```markdown
# UI/UX 體檢

整體：3.1 / 5（各畫面平均）

| 畫面 | 視覺層級 | 一致性 | 排版節奏 | 回饋 | 文案 | 效率 | 質感 | 平均 |
|---|---|---|---|---|---|---|---|---|
| S2 訂單列表 | 4 | 3 | 3 | 2 | 4 | 3 | 3 | 3.1 |

## S2 訂單列表
- 回饋 2：API 失敗時永遠停在「載入中…」（F31）；刪除後沒有任何提示。要到 4 分：需要錯誤狀態、重試按鈕，以及刪除成功的提示。
- 一致性 3：主要和次要按鈕的圓角不同（F21）；量化檢查：圓角 2 種、字級 5 種。
- …

## 最值得做的 5 項改善

照「對使用者的影響 ÷ 改動大小」排序：

1. **建立表單加上即時驗證和欄位層級的錯誤訊息**
   - 現況：漏填時只顯示「發生錯誤」（F3），數量可以是負數（F4）
   - 建議：必填欄位加上標示，離開欄位時就驗證，錯誤訊息顯示在欄位下方
   - 預期效果：減少送出失敗和髒資料；回饋、文案兩個維度預期可以到 4 分
2. …
```

改善建議要具體到工程師或設計師拿了就能動手。「優化使用者體驗」這種寫法不算一項建議。
