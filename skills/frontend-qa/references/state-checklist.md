# 狀態檢查清單

每個畫面都逐項檢查。某一項不適用時，在 `coverage.md` 的備註寫明哪幾項不適用，以及為什麼。

## 既有資料抽樣

自己建立的資料只會有你填過的欄位。很多 bug 只出現在既有資料上，例如舊資料少了某個欄位，或狀態是你建立不出來的。

步驟 1 偵察時，先把既有資料按型態分組，例如：
- 每一種狀態（待處理、已完成、已取消…）
- 選填欄位缺漏或為空
- 很長或含特殊字元的內容
- 數值極端的資料

接著在 `coverage.md` 的備註中，記下每一組各抽了哪一筆。

`狀態` 這一輪，每一組都要打開列表、詳情和編輯畫面至少各一次，並檢查 console。只用自己建立的資料測過的項目，不能打勾。

## 資料狀態

- [ ] **空狀態**：沒有任何資料時，畫面是否說明現在的情況，並提供下一步（例如「建立第一筆」）
- [ ] **載入中**：有沒有骨架畫面或 spinner；載入完成時版面會不會跳動
- [ ] **錯誤**：API 失敗時，錯誤訊息是否說明發生什麼事、使用者能做什麼，以及有沒有重試的方式
- [ ] **部分失敗**：列表裡有幾筆失敗時，其他筆是否仍能正常顯示
- [ ] **大量資料**：100 筆以上時，有沒有分頁或虛擬捲動、效能是否可接受、篩選和搜尋是否正確
- [ ] **極端值**：數字 0、負數、極大值、小數，日期為今天、跨年、時區邊界
- [ ] **長內容**：長標題、長名稱、沒有空格的長字串，是否會截斷、換行或撐破版面
- [ ] **權限**：沒有權限的使用者，看到的是隱藏的元件、停用的元件，還是點下去才報錯；三種處理方式在整個 app 中是否一致

## 互動狀態

- [ ] **送出後**：有沒有成功回饋；按鈕是否進入 loading 或停用狀態以防止重複送出
- [ ] **未存離開**：離開有未儲存內容的頁面時，有沒有提示
- [ ] **復原**：刪除或其他破壞性操作，有沒有確認步驟或復原方式
- [ ] **重新整理**：重新整理後，篩選條件、分頁、分頁籤、捲動位置等狀態是否合理保留
- [ ] **深層連結**：直接打開某個子頁的網址能不能正常進入；登入後是否會回到原本要去的頁面

## 易用性原則（Nielsen 10）

逐條檢查，違反就記錄下來，並在類別欄註明違反的是哪一條。

1. **系統狀態可見**：使用者是否隨時知道現在發生什麼事
2. **貼近真實世界**：用的是不是使用者的語言，而不是內部術語
3. **使用者有控制權**：有沒有取消、返回、復原的方式
4. **一致性**：同一件事是否用同一種名稱、同一種樣式、同一種位置
5. **預防錯誤**：是否在錯誤發生之前就擋下，而不是事後才報錯
6. **辨識優於回憶**：選項是否看得見，而不是要使用者自己記得
7. **彈性與效率**：常用操作有沒有捷徑
8. **簡約設計**：有沒有無關的資訊在搶注意力
9. **錯誤恢復**：錯誤訊息是否說明原因和解決方法
10. **說明文件**：需要時找不找得到幫助

## 主控台與網路

每個畫面測完時檢查：

- [ ] console 有沒有新的錯誤或 exception（`console <t> --errors`）
- [ ] 有沒有失敗的請求（`netlog <t> --status 4xx`、`netlog <t> --status failed`）
- [ ] 有沒有明顯重複或多餘的請求，例如同一支 API 在一次操作中被打了好幾次

如果 console 出錯，但畫面上看不出影響，記為 P2，類別填「bug」，並在證據中附上錯誤訊息。
