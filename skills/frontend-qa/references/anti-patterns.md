# 反模式

常見的設計錯誤。標準和深的體檢、`critique` 評分時對照這份清單，見 [ux-review.md](ux-review.md#對照反模式)。`audit` 只收可以用 `eval` 偵測的條目。

每一條的「元素」寫成 `selector "可見文字"`，和探測結果同一套。可以用 `eval` 偵測的，程式在 [`scripts/anti-patterns.js`](../scripts/anti-patterns.js)，探測腳本會一併跑。超過條件不一定就是錯，但要寫出理由。不要因為清單裡有這一條就自動降分；分數仍照 [ux-review.md](ux-review.md#分數錨點)。

## 同一區塊有多顆一樣重的主要按鈕

- check：`multiple-primary-buttons`
- 怎麼看出來：`eval`。同一個父元素底下，有兩顆以上可見的按鈕或連結，背景不是透明、飽和度大於 0.15，而且背景色和文字色彼此相同。
- 對應維度：視覺層級
- 怎麼改：只留一顆實心主要按鈕，其餘改成外框或文字按鈕。

## 對話框問句和按鈕語意不符

- check：`generic-dialog-actions`
- 怎麼看出來：`eval`。可見的 `[role=dialog]`、`dialog` 或 `[aria-modal=true]` 裡，文字含 `嗎`、`？` 或 `?`，而且按鈕文字全部是 `確定` / `取消` / `OK` / `Cancel` / `Yes` / `No`，至少兩顆。
- 對應維度：文案
- 怎麼改：按鈕寫出動作本身，例如 `放棄變更` / `繼續編輯`，不要只寫 `確定` / `取消`。

## 用 placeholder 當 label

- check：`placeholder-as-label`
- 怎麼看出來：`eval`。可見的 `input` 或 `textarea` 有 `placeholder`，但沒有包住它的 `label`、`label[for]`、`aria-label`、`aria-labelledby` 或 `title`。
- 對應維度：文案
- 怎麼改：加上永遠看得到的 label。placeholder 只放範例格式。

## 只用顏色區分狀態

- check：`color-only-status`
- 怎麼看出來：`eval`。同一個父元素底下有兩個以上可見、沒有文字、沒有 `aria-label` 或 `title`、沒有 `img` 或 `svg`、寬和高都不超過 16px 的元素，而且背景色至少兩種。
- 對應維度：回饋
- 怎麼改：狀態加上文字或圖示名稱，顏色只當輔助。

## 灰字放在彩色背景上

- check：`gray-on-color`
- 怎麼看出來：`eval`。元素自己的文字色飽和度低於 0.15、明度在 0.25 和 0.75 之間（灰，不是接近黑或接近白），背後第一層不透明背景的飽和度大於 0.35。
- 對應維度：質感
- 怎麼改：灰字放回中性背景，或改成白字、深色字，讓它和彩色背景是一組。

## 卡片裡又包卡片

- check：`nested-cards`
- 怎麼看出來：`eval`。可見元素的圓角至少 4px、有不透明背景，而且有邊框或陰影；它的祖先（往上最多 8 層，不含幾乎全螢幕的外框）也是這樣。按鈕、連結、輸入、標題、段落不算卡片。
- 對應維度：視覺層級
- 怎麼改：拿掉內層的邊框、陰影或圓角，讓一層卡片就夠。

## 長段落置中對齊

- check：`centered-long-text`
- 怎麼看出來：`eval`。`p`、`div` 或 `li` 的 `text-align` 是 `center`，自己的文字至少 40 個字，而且不在按鈕、連結、標題或 `th` 裡面。
- 對應維度：排版節奏
- 怎麼改：長文改靠左（或靠起始邊）。置中只留給短標題。

## 空狀態只寫「無資料」，沒有下一步

- check：`empty-state-no-action`
- 怎麼看出來：`eval`。元素自己的文字符合「無資料 / 沒有資料 / 暫無資料 / 尚無資料 / no data / nothing here / no results」，父元素的可見文字不超過 80 個字，而且裡面沒有連結或按鈕。
- 對應維度：文案、效率
- 怎麼改：寫出為什麼是空的，並給一個下一步按鈕或連結。

## 錯誤訊息只寫「發生錯誤」

- check：`vague-error`
- 怎麼看出來：`eval`。可見元素自己的文字整段就是「發生錯誤」「發生了一些錯誤」「錯誤」「something went wrong」「an error occurred」或「error」，後面最多一個句號。
- 對應維度：文案、回饋
- 怎麼改：寫出原因和使用者下一步可以做什麼，放在相關欄位旁邊。

## 錯誤用 toast 顯示，而且很快就消失

- check：無（不是頁面載入當下的 `eval`）
- 怎麼看出來：目視。操作之後錯誤出現在 toast、snackbar 或短暫的 `[role=alert]`，幾秒內從畫面上消失，欄位或頁面上沒有留下同一則訊息。
- 對應維度：回饋
- 怎麼改：錯誤留在觸發它的欄位或表單上，直到使用者改完。toast 只用在不需要事後回看的成功提示。

## 破壞性動作和主要動作外觀相同

- check：`destructive-looks-primary`
- 怎麼看出來：`eval`。按鈕文字符合刪除、移除、作廢、delete、remove、destroy，另一顆符合新增、建立、儲存、送出、確認、save、create、submit、add；兩顆都是飽和度大於 0.15 的實心底，而且背景色和文字色相同。
- 對應維度：視覺層級
- 怎麼改：破壞性動作用別的顏色或外框，和主要動作分開。確認文案要寫出會刪掉什麼。

## 表單送出後沒有任何狀態變化

- check：探測的 `no-feedback`（離線或 API 500）。成功路徑沒有單獨的 `eval` check。
- 怎麼看出來：操作前後比較畫面文字、網址和按鈕狀態。什麼都沒變就是命中。探測腳本的 `no-feedback` 涵蓋離線和 API 500 這兩種失敗送出，見 [probe.md](probe.md#檢查項目)。
- 對應維度：回饋
- 怎麼改：送出後立刻給處理中狀態；成功或失敗都要有留在畫面上的說明。
