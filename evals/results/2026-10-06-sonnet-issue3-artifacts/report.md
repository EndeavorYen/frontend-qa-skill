# 前端 QA 報告：小訂單（整個 app）

## 範圍
- 日期：2026-10-06；環境：本機測試環境；URL：http://localhost:4174（hash 路由 SPA）
- 測試帳號：任意帳密（`a`、`qa`），登入後為單一身分；沒有多角色，所以沒有角色切換測試
- 範圍：整個 app —— 登入、訂單列表（篩選、刪除）、訂單詳情、建立訂單、設定、說明、聯絡我們、404。沒有縮小範圍
- 禁止動作：本機環境，使用者明確允許所有操作（含建立、刪除訂單）；測試中建立過約 60 筆測試訂單並已刪除，結束時資料回到初始的 #1–#3
- 方式：黑箱，沒有讀取 app 的 JS／CSS 原始碼；只用畫面、DOM、console、網路請求（console 堆疊中出現的 `app.js:行號` 是 console 輸出，不是讀原始碼）
- 視窗尺寸：桌機 1280x800、手機 390x844、320x568（深度 4；不含深色模式 —— app 也沒有提供）
- 深度與面項：深度 4；新手、亂點、設計師、小螢幕鍵盤、惡劣環境、狀態、體檢（深）、工具軌 全開
- 工具：chrome-cdp-ex `2bd2728`（2.20.0），HeadlessChrome 153.0.8010.12，Node v22.22.3，Linux 6.8
- 成本：估算約 162 turns、28 分鐘、US$7.5；實際約 115 turns、分鐘數未知（無計時）、US$約 4.1（Sonnet 5.5；以對話預算計數器為準）

## 估算
- 深度 4；面項：新手、亂點、設計師、小螢幕鍵盤、惡劣環境、狀態、體檢、工具軌
- 覆蓋地圖：12 列 × 6 輪 = 72 格；體檢 8 個畫面
- 估算：20 + 72×1.7 + 8×2.5 ≈ 162 turns、約 28 分鐘、US$7.5
- 實際比估算少，原因：多個格子可以用同一批 `eval` 一次跑完（例如對 5 個畫面同時量化檢查），且靜態頁（S6–S8）只有一個元件。

## 摘要
- 嚴重度（合併重複後 39 個問題）：P0 ×0、P1 ×4、P2 ×20、P3 ×15（F36 併入 F18、F39 併入 F2，所以 F1–F41 共 39 個獨立問題）
- 覆蓋率：✅ 59 / ➖ 13 / ⛔ 0（總共 72 格，不含體檢）；體檢 ✅ 8 / ➖ 4（流程列）
- 一句話結論：這個 app 的「正常路徑」大致能用，但**幾乎沒有錯誤處理**：只要 API 回 500、斷網、連點、輸入不合理的值，就會建立重複／負數訂單、丟失資料、卡在「載入中…」或顯示 `undefined`；設定頁的「已儲存」是假的。

## 最嚴重的 5 個問題
1. F10 [P1][邏輯] 設定頁按「儲存」顯示「已儲存」，但沒有任何請求、重新整理後全部還原 —— 使用者以為已關閉 Email 通知，其實沒有
2. F37 [P1][bug] 建立訂單 API 回 500 時，畫面跳到空白的 `#/orders/undefined`，已填資料消失、沒有錯誤訊息
3. F12 [P1][bug] 連點「送出訂單」會建立重複訂單（按鈕不停用、送出約 800ms 無任何回饋）：連點 3 次建立 3 筆、2 次建立 2 筆
4. F32 [P1][RWD] 320x568 手機上，固定頁尾蓋住建立訂單頁的「送出訂單」（只剩 9/41px 可見）
5. F17 [P2][bug] 狀態篩選「已完成」顯示全部訂單（含待處理）；同類的 F13（負數／0／小數數量可送出，小計變負）、F35（列表 500/401 永遠「載入中…」）也很影響信任

## UI/UX 體檢摘要
- 整體 2.3 / 5；最低分的畫面：S6 說明、S7 聯絡我們、S8 404（各 2.0，頁尾兩個連結都是死路）；最高：S1 登入（3.1）
- 最值得做的 3 項改善（完整內容見 `ux-review.md`）：
  1. 所有 API 呼叫統一處理失敗＋送出時鎖住按鈕（解掉 F12、F35、F37、F38、F40、F2、F21）
  2. 設定頁真的儲存，並讓「每頁筆數」生效／加分頁（F10、F11）
  3. 建立訂單表單加欄位層級驗證，提示文字改成看得到（F4、F13、F24）
